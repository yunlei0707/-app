# SDK按钮问题完整复盘文档 v1.0

## 📋 第一部分：具体操作流

### 问题背景
这次遇到的三个核心问题：
1. **SDK按钮不显示** - 初始化冲突或加载失败
2. **底部导航"我的"tab被误抓** - 变成可拖拽的浮动元素，不在底部导航了
3. **页面下方有大量代码泄漏** - CSS没有正确包裹

---

### 完整排查过程

#### 🔍 问题1：页面下方大量代码泄漏

**排查步骤：**
1. 用 `wc -l index.html` 发现文件有601行，异常大
2. 用 `grep -n "<style\|</style" index.html` 发现只有`</style>`结束标签，没有开始标签
3. 确认CSS代码直接暴露在HTML里，没有被`<style>`标签包裹

**解决方法：**
- 从干净版本v2.5.10（e88e666）恢复，这个版本的CSS正确包裹在第23-132行的`<style>`标签内

---

#### 🔍 问题2：底部导航"我的"tab被误抓，变成可拖拽

**排查步骤：**
1. 检查index.html里的SDK定制代码，发现有自动识别SDK按钮的逻辑：
   ```javascript
   // 问题代码：只要宽度40-80px，高度40-80px，包含svg就被识别为SDK按钮
   if (style.position === 'fixed' && 
       rect.width > 40 && rect.width < 80 && 
       rect.height > 40 && rect.height < 80 &&
       btn.querySelector('svg')) {
     // 当成SDK按钮，添加拖拽功能，设置position: fixed
   }
   ```
2. 底部导航"我的"tab正好符合：宽度64px，高度64px，包含User图标（svg）
3. 所以被这段代码错误地把"我的"tab当成了SDK按钮，从底部导航中"抓"出来，变成可拖拽的浮动元素！

**解决方法：**
- 添加**logo/icon关键字检查**，只有包含logo/icon的按钮才会被识别为SDK按钮：
  ```javascript
  const hasLogoKeyword = className.includes('logo') || className.includes('icon') ||
                        innerText.includes('logo') || innerText.includes('icon');
  
  if (style.position === 'fixed' && 
      rect.width > 20 && rect.height > 20 && 
      rect.left > window.innerWidth - 150 &&
      hasLogoKeyword) {  // ✅ 必须包含logo/icon关键字，不会误抓底部导航
    // 只有真正的SDK按钮
  }
  ```

---

#### 🔍 问题3：SDK按钮不显示

**排查步骤：**
1. 发现有两个地方同时初始化SDK：index.html和FloatingButton.jsx，导致冲突
2. CDN加载不稳定，有时候加载失败
3. 初始化时机不对，SDK脚本还没加载完就初始化

**解决方法：**
1. 只保留一个地方初始化SDK，避免冲突
2. 用**本地静态SDK文件** `/static/coze-chat-sdk.js`（738KB完整文件），代替CDN，加载更稳定
3. 延迟800ms初始化，确保SDK脚本加载完成

---

### 最终解决方案汇总

| 问题 | 根本原因 | 解决方案 |
|------|----------|----------|
| 页面下方大量代码 | CSS没有被`<style>`标签包裹 | 从干净版本恢复，确保CSS正确包裹 |
| "我的"tab被误抓 | SDK按钮识别条件太泛，只有尺寸+svg | 添加logo/icon关键字检查 |
| SDK按钮不显示 | 两处同时初始化冲突 + CDN不稳定 | 只保留一处初始化 + 用本地静态SDK文件 |

最终版本：313行，CSS和JS都正确包裹，SDK按钮正常显示且不误抓底部导航！

## ⚠️ 第二部分：SDK沙箱和白名单限制

### 关键前提：SDK本身的限制，调用前就要知道

扣子SDK有严格的**沙箱机制**和**白名单限制**，不是所有操作都能做的！这个是**事前就要知道**的，不要事后折腾半天发现做不到。

---

### 一、SDK沙箱限制：哪些能做，哪些不能做

| 操作 | 能不能做 | 说明 |
|------|----------|------|
| ✅ 修改SDK按钮的样式 | 能 | background、border-radius、box-shadow等样式可以改 |
| ❌ 给SDK按钮加拖拽功能 | **不能** | SDK内部会强制重置位置，拖了马上弹回去！我们今天试了好久就是这个问题！|
| ✅ 延迟SDK初始化时间 | 能 | 自己控制初始化时机 |
| ❌ 移动SDK按钮的默认位置 | 不能 | SDK内部会强制重置位置，改了也会被弹回去 |
| ❌ 修改SDK按钮的内部结构 | 不能 | 沙箱隔离，无法访问iframe内部DOM |
| ❌ 监听SDK按钮的点击事件 | 不能 | 沙箱隔离，无法捕获内部事件 |
| ❌ 隐藏SDK按钮只显示我们自己的按钮 | 不能 | SDK会自动创建按钮，我们自己的按钮会被拦截 |
| ❌ 修改SDK聊天窗口的内容 | 不能 | 完全在沙箱iframe内部 |

---

### 二、我们踩过的坑（因为不知道沙箱限制）

1. **最大的坑：想给SDK按钮加拖拽功能**
   - 结果：我们今天试了好几个小时，代码写了一大堆，拖了马上被SDK弹回去！
   - 根本原因：SDK内部有定时器，会强制把按钮位置重置回右下角！
   - 教训：SDK按钮的位置是完全锁定的，动不了！

2. **坑2：想把SDK按钮移到底部导航的空位上**
   - 结果：改了right/bottom，SDK内部会自动重置位置，白折腾
   - 教训：SDK按钮只能在右下角，不能移到其他地方

3. **坑3：想移除SDK按钮里的"美化输出"按钮**
   - 结果：移除不了，因为在iframe沙箱里，我们访问不到
   - 教训：沙箱内部的东西我们完全控制不了

---

### 三、正确的做法：调用插件前先了解限制

#### 1. 事前调研
- 先看SDK文档，了解有什么API，有什么限制
- 不要想当然"应该能做到"，很多事情沙箱不允许
- 先做最小可行性验证，不要一开始就写很多代码

#### 2. 只在允许的范围内做增强
- ✅ 可以做的：美化SDK按钮样式
- ❌ 不要碰的：SDK按钮的位置、SDK内部的任何东西、拖拽功能
- 记住：我们只能给SDK按钮"化妆"，不能给SDK"动手术"

#### 3. 遇到限制就绕路，不要硬刚
- 如果SDK不让改位置，那就接受它在右下角
- 如果SDK不让移除某个按钮，那就想其他办法（比如用CSS遮罩，但也要看能不能穿透）
- 硬刚沙箱只会浪费时间，还会引入更多问题

## 📚 第三部分：工作方法论

### 一、设计时就避免问题（事前预防）

#### 1. 代码包裹规范
- **CSS必须100%正确包裹在`<style>`标签内，**不能直接写在HTML里
- **JS必须100%正确包裹在`<script>`标签内
- 写完一定要用 `grep -n "<style\|</style\|<script\|</script" index.html` 检查是否匹配

#### 2. 元素识别一定要精确匹配
- ❌ 不要用太泛的条件：`宽度40-80px + 包含svg` → 太容易误抓
- ✅ 一定要加**关键字检查**：`包含logo/icon关键字` + `在右边区域`
- 识别条件越精确越好，宁可漏识别也不要误识别

#### 3. 初始化代码规范
- ❌ 不要在多个地方同时初始化同一个SDK
- ✅ 只保留一个入口点初始化
- ✅ 加防重复初始化标记：`if (window.xxxInitialized) return`
- ✅ 延迟初始化，确保脚本加载完成：`setTimeout(init, 800)`

#### 4. 资源加载规范
- ❌ 不要过度依赖第三方CDN，CDN可能被墙、可能超时、可能版本更新
- ✅ 重要资源用**本地静态文件**，加载更稳定，不受外部影响

#### 5. SDK沙箱限制提前调研
- ❌ 不要想当然认为能修改SDK按钮的默认位置、加拖拽功能
- ✅ 先看文档，了解沙箱能做什么、不能做什么
- ✅ 只在允许的范围内做增强：美化样式
- ✅ 遇到限制就接受，不要硬刚沙箱

---

### 二、问题排查方法论（事中处理）

#### 1. 先找稳定版本作为基准
- 用户明确说哪个版本是稳定的，先从那个版本出发
- 不要在问题版本上反复修改，越改越乱
- 用 `git log --oneline -50` 找历史版本
- 用 `git show <commit>:<file>` 看某个版本的文件内容

#### 2. 逐行对比，找差异
- 用 `wc -l index.html` 看文件行数，行数异常大的肯定有问题
- 用 `diff <(git show commit1:index.html) <(git show commit2:index.html)` 对比两个版本
- 重点看：`<style>`、`<script>`标签是否匹配

#### 3. 关键位置打日志
- 在SDK初始化前后打console.log
- 在按钮识别逻辑里打日志，看识别到了什么按钮
- 看控制台有没有JS报错

#### 4. 分模块测试，不要一下子加很多功能
- 先测试SDK按钮能不能正常显示
- 再加其他增强功能
- 每加一个功能，测试一次

#### 5. 遇到奇怪的问题，先想想是不是沙箱限制
- 比如改了SDK按钮的位置又弹回去 → 这是SDK内部重置，不是我们代码的问题
- 比如点击事件没反应 → 可能被SDK拦截了
- 比如找不到某个元素 → 可能在iframe沙箱里，我们访问不到

---

### 三、问题解决方法论（事后复盘）

#### 1. 从稳定版本出发，逐步添加功能
- 先恢复到稳定版本，确保基础功能正常
- 然后一个功能一个功能地加
- 每加一个功能，测试验证一次
- 不要一下子把所有功能都加上，出问题不知道是哪个导致的

#### 2. 遇到问题立即回滚，不要在问题版本上死磕
- 如果加了某个功能后出问题，立即回滚到上一个稳定版本
- 然后单独测试那个功能，找出问题所在
- 不要在已经出问题的版本上反复修改，越改越乱

#### 3. 关键检查一定要有，避免误伤
- 自动识别按钮、自动修改DOM的代码，一定要有关键检查
- 比如识别SDK按钮，一定要有logo/icon关键字检查
- 宁可漏识别，也不要误识别
- 误识别的后果比漏识别严重得多

#### 4. 保留完整的版本历史，方便回溯
- 每次提交时写清楚commit message，说明改了什么
- 方便以后出问题时回溯
- 用 `git log --oneline` 就能快速找到需要的版本

---

## ✅ 最终总结

这次问题的6条核心教训：

1. **代码包裹是基础** - CSS和JS一定要正确包裹，否则直接泄漏到页面上
2. **自动识别要精确** - 元素识别条件一定要精确，加关键字检查，避免误伤
3. **初始化要单一** - 不要多个地方同时初始化同一个SDK，会冲突
4. **资源要本地** - 重要资源用本地静态文件，比CDN稳定
5. **从稳定版本出发** - 遇到问题先回滚到稳定版本，再逐步排查
6. **SDK沙箱限制要提前知道** - 不是所有操作都能做，调用前先调研，只在允许的范围内做增强，不要硬刚沙箱
